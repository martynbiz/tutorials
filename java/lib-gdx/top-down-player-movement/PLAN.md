# Top-Down Player Movement: implementation plan

How the series specified in [SPEC.md](SPEC.md) gets built: a working reference project, built guide by guide, and the README and five guides written from it.

## Context

The decisions are fixed in [SPEC.md](SPEC.md), so this plan doesn't repeat or revisit them. In short:
- **The series:** a README and five guides in this folder, using the reader's own 8-direction sheet.
- **The code:** Ashley systems split by behaviour.
- **The rules:** movement, attack and rendering behave as the spec sets out.
- **No automated tests.**

### Stack

| Choice | Value | Source |
|---|---|---|
| Language | Java. The JDK installed here is Temurin 25.0.2. The language level the project targets is set by what liftoff's Gradle supports (milestone 0) | Spec, and checked on this machine |
| Framework | libGDX, desktop only, LWJGL3 backend | Spec |
| Entity component system | Ashley | Spec |
| Build | Gradle with its wrapper, generated by gdx-liftoff (`core` and `lwjgl3` modules) | Spec |
| Tests | None, by decision. Verification is by running the game | Spec |
| Workflow | No TDD. Each milestone is built, run and checked by hand | Follows from "no tests" |
| Docker, deployment | Not applicable: it's a desktop tutorial project | |
| README | Yes: the series README in this folder, started in milestone 1 and finished in milestone 6 | Spec, and the repo's [CLAUDE.md](../../../CLAUDE.md) |

### Where things live

- **Guides, README, spec and plan:** this folder, `java/lib-gdx/top-down-player-movement/`. Only these are committed.
- **Reference project:** built in the session scratchpad, at `…/scratchpad/top-down/code/`. It's a local git repo with one commit per guide, tagged `guide-01` to `guide-05`, the same way the Consuming APIs series was built. It's never committed to the tutorials repo.
- **Test sheet:** a sheet that meets the requirement, used for building and screenshots. It's kept at `…/scratchpad/top-down/test-sheet/` and copied into the reference project's `assets/`. It's never committed to the tutorials repo, and never named in the guides.
- **Java package:** `com.example.topdown`, matching the repo's `com.example.*` convention. Within it:
  - `graphics/` holds the `SpriteSheet` class and the mapping block
  - `components/` and `systems/` hold the Ashley classes
- **Guide files:**
  - `01-drawing-the-player.md`
  - `02-reading-a-sprite-sheet.md`
  - `03-entities-and-systems.md`
  - `04-eight-direction-movement.md`
  - `05-attacking.md`

### Guide format

Same as the repo's other series:
- an intro and a "what you'll build" summary
- numbered steps with full code for each file they touch
- "Your turn" exercises with solutions
- a "Checkpoint" saying what the game should look like
- a recap, and a link to the next guide

Exercises only practise material that's already been taught: anything new gets taught as a step first.

## Milestones

### 0. [ ] Versions and the test sheet's row map

Settles the facts every later milestone depends on.

- **Versions.** Look up the current gdx-liftoff release, and the libGDX, Ashley and Gradle versions it generates. Check whether that Gradle runs on Java 25, and which Java language level liftoff targets. Record the results in `…/scratchpad/top-down/BUILD-NOTES.md` for the README versions table.
- **Generating the project.** gdx-liftoff is a desktop app with a form, so first find out whether it can be run headless. If it can't, see open question 1.
- **Test sheet row map.** Read the test sheet the way guide 02's checklist will tell readers to, and record in `BUILD-NOTES.md`:
  - the frame size of each file
  - which rows hold idle, walk and attack, and for which of the 8 directions
  - the frame counts, and any empty cells

  These numbers drive the reference project. The guides only quote them as illustrations, without naming the sheet. Any animation the test sheet only has in 4 directions isn't used.

**Verify:**
- `BUILD-NOTES.md` has a versions table and a row map giving a direction for all 8 directions of idle, walk and attack.
- Every row in the map has been checked by cutting its frames out and looking at them, not by reading the sheet as a whole.

### 1. [ ] Guide 01: Drawing the player, and the README skeleton

**Depends on:** milestone 0.

**Delivers:** a liftoff project that opens a 1280×720 window and draws one frame of the test sheet in the centre, crisp and scaled up, through a 320×180 `FitViewport`.

**Reference project files:**
- generated by liftoff, with no hand edits except where the guide says so: `settings.gradle`, `build.gradle`, `gradle.properties`, `gradlew`/`gradlew.bat`, `gradle/wrapper/`, `core/build.gradle` and `lwjgl3/build.gradle`
- `lwjgl3/src/main/java/com/example/topdown/lwjgl3/Lwjgl3Launcher.java`: liftoff's launcher, with the window size and title set
- `core/src/main/java/com/example/topdown/TopDownGame.java`: the game class (`ApplicationAdapter`), with `create`, `render`, `resize` and `dispose`, `OrthographicCamera` + `FitViewport`, `SpriteBatch`, a `Texture` with `Nearest` filtering, and one `TextureRegion` drawn at the centre. The class name follows what liftoff generates, which might be `Main`, and the guide uses whichever it is
- `assets/`: the reader's sheets

**Guide (`01-drawing-the-player.md`) covers:**
- the sheet requirement, repeated from the README
- generating the project with liftoff: the form fields, desktop only, Ashley ticked, and where the Ashley dependency line ends up
- the project layout
- the game loop and delta time
- textures, regions and disposing them
- camera, viewport and world units
- the "why it's blurry" note on `Nearest`
- running with `gradlew lwjgl3:run`

**README.md (skeleton):**
- what the series builds
- **the sheet requirement**, prominently, before guide 01
- what readers need to know already
- a versions table filled in from milestone 0
- the guide list, with only guide 01 linked so far
- a "where things live" tree of the reader's project
- how to run it

**Verify:**
- `gradlew build` and `gradlew lwjgl3:run` work from a clean checkout of tag `guide-01`.
- A screenshot shows one crisp frame centred in a 1280×720 window.
- Resizing the window gives black bars, not stretching.
- Each Your turn solution has been run.

### 2. [ ] Guide 02: Reading a sprite sheet

**Depends on:** milestone 1.

**Delivers:** the `SpriteSheet` class and the mapping block, and one walk cycle playing on the spot through libGDX's `Animation`.

**Reference project files:**
- **`core/…/graphics/SpriteSheet.java`**:
  - the constructor takes the texture and the frame width and height, and works out the columns and rows itself
  - `frame(row, col)` and `framesSequence(row, col, count)` return `TextureRegion`s, built on the author's flat-numbering helpers, with deliberate wrapping into the next row
  - a row or column that doesn't exist stops with a clear `IllegalArgumentException`, such as "row 9 doesn't exist: this sheet has 8 rows"
- **`core/…/graphics/PlayerSheets.java`**: the **mapping block**. It holds:
  - the sheet paths and frame sizes as constants
  - for walking: the start row and column, the frame count and the frame duration

  It grows in milestones 4 and 5 into the full set of animations, and is the one file a reader edits for their own sheet.
- **`TopDownGame.java`**: builds an `Animation<TextureRegion>` from `framesSequence`, keeps a state time, and draws `getKeyFrame(stateTime, true)`.

**Guide (`02-reading-a-sprite-sheet.md`) covers:**
- how a sheet is laid out
- flat frame numbering, with a worked example
- the "Reading your sheet" checklist and the table to fill in
- `TextureRegion.split`, or slicing by hand, whichever the `SpriteSheet` code uses, explained
- `Animation`, `PlayMode` and state time
- what the error message means

**Verify:**
- The walk cycle plays smoothly on the spot, checked with a few screenshots a frame-duration apart or a short screen recording.
- Deliberately using a row past the end stops with the clear message.
- Each solution has been run.

### 3. [ ] Guide 03: Entities and systems

**Depends on:** milestone 2.

**Delivers:** the same walk cycle on screen, now made of an Ashley entity and its systems.

**Reference project files:**
- **`core/…/components/`**: `Position.java`, `Sprite.java` (the current `TextureRegion`), `Animations.java` and `State.java`.
  - `State` holds the state, facing and state time. In this guide the only state is `WALK` and the facing is fixed, so `Animations` maps a state to one animation.
  - Milestone 4 adds `Direction` and makes the map state and direction to animation.
  - Each component implements Ashley's `Component` and has a `ComponentMapper`.
- **`core/…/systems/AnimationSystem.java`**: an `IteratingSystem` for entities with `Animations` and `State`. It advances the state time and sets `Sprite` to the current frame.
- **`core/…/systems/RenderSystem.java`**: an `IteratingSystem` for entities with `Position` and `Sprite`. It draws through the shared `SpriteBatch` and camera.
- **`TopDownGame.java`**: creates the `Engine`, adds the systems in priority order, builds the player entity from `PlayerSheets`, and calls `engine.update(delta)` in `render`.

**Guide (`03-entities-and-systems.md`) covers:**
- what an entity component system is
- why systems are split by behaviour and not by character, with the `HeroAnimationSystem` counter-example
- components, entities, `Family`, `ComponentMapper`, `IteratingSystem` and system priority (order)
- where the `SpriteBatch` `begin`/`end` calls go

**Verify:**
- On screen it's identical to guide 02, checked by comparing screenshots.
- Each solution has been run.

### 4. [ ] Guide 04: Eight-direction movement

**Depends on:** milestone 3.

**Delivers:** the arrow keys move the player in 8 directions at the same speed on the diagonals. The player faces the way it moves, and stops and idles in its last direction.

**Reference project files:**
- **`core/…/Direction.java`**: an enum of 8 values. It maps a non-zero input vector to the nearest direction.
- **New components:** `Velocity.java` and `PlayerControlled.java`. `State` gains `IDLE`, and `Animations` becomes state and direction to animation.
- **`core/…/systems/PlayerInputSystem.java`**: reads `Gdx.input` for the arrow keys. It builds the input vector with opposite keys cancelling, normalises it, multiplies by the speed (about 60 px/s), and sets the velocity, the facing, and `WALK` or `IDLE`.
- **`core/…/systems/MovementSystem.java`**: position += velocity × delta.
- **`PlayerSheets.java`**: idle and walk entries for all 8 directions.

**Guide (`04-eight-direction-movement.md`) covers:**
- polling the keyboard
- turning keys into a vector
- the √2 diagonal bug, with a worked example, and normalising it away
- delta time and speed
- vector to `Direction`
- why facing is stored apart from velocity
- the idle and walk switch, and resetting the state time when the animation changes

**Verify, by running the game:**
- Each of the 8 key combinations walks the right way with the right frames.
- A diagonal covers the same distance per second as a straight line, checked by logging the position over a fixed time during development, then removing the logging.
- ← + → stands still, and ← + → + ↑ walks straight up.
- Releasing the keys idles, facing the last direction.
- The player can walk off screen.
- Each solution has been run.

### 5. [ ] Guide 05: Attacking

**Depends on:** milestone 4.

**Delivers:** Space plays the attack once in the direction faced, without the player jumping when the attack frames are a different size from the walk frames, then returns to idle, or to walking if keys are held.

**Reference project files:**
- **`State`**: gains `ATTACK`.
- **`PlayerInputSystem`**:
  - Space is read with `isKeyJustPressed`, set as one constant, and ignored during an attack.
  - During an attack, velocity is zero and the facing is locked.
  - When the attack ends, the state is set from the keys held at that moment.
- **`AnimationSystem`**: attack animations use `PlayMode.NORMAL`. When `isAnimationFinished`, the state goes back to idle or walk.
- **`RenderSystem`**: draws frames centred on the feet, with the position at the bottom centre of the frame, and adds the per-animation offset.
- **`PlayerSheets.java`**: attack entries for all 8 directions, and an optional offset per animation.

**Guide (`05-attacking.md`) covers:**
- the three-state diagram: `IDLE`, `WALK`, `ATTACK`
- "just pressed" against "held"
- animations that play once
- locking movement and facing during an attack
- frame sizes and anchoring at the feet, with before and after screenshots showing the jump
- offsets for sheets whose character isn't centred
- "Where next", listing the spec's non-goals

**Verify, by running the game:**
- The attack plays in all 8 directions.
- Nothing jumps when the attack frames start, compared with the guide's "before" screenshot.
- Holding Space attacks only once.
- Pressing Space mid-attack does nothing.
- With an arrow key held, the player walks on as soon as the attack ends.
- Each solution has been run.

## Open questions carried forward

1. **Generating the project (blocks milestone 1).** The guide tells readers to use gdx-liftoff's form, but building needs a project the builder can generate. Options:
   - run liftoff headless, if it supports that
   - recreate its output from its templates on GitHub
   - the author runs liftoff once with the settings from guide 01 and shares the folder

   Milestone 0 finds out which is possible. If the result isn't liftoff's real output, guide 01's file listings and screenshots of the form need a check by the author.
2. **Java version (blocks milestone 1).** Only Java 25 is installed. If liftoff's Gradle doesn't run on 25, the guide either tells readers to install an older JDK or upgrades the Gradle wrapper. Settled in milestone 0 from what actually builds.
3. **The test sheet's row meanings (blocks milestone 2).** They're worked out by eye in milestone 0. If any direction is ambiguous, the author confirms it.
4. **Visual checks.** The builder checks motion through screenshots and position logs, which can't fully show smoothness. The author's own run in milestone 6 is the final check.
5. **Scratchpad copies.** The reference project and the test sheet live in the scratchpad, which a reboot or cleanup can wipe. The guides are written as each milestone completes, so a loss costs rebuilding, not the guides. The author keeps their own copy of the test sheet.

## Out of scope

From the spec's non-goals; these aren't to be picked up mid-build:
- enemies, collisions and tile maps
- hit boxes and damage
- a camera that follows the player, and keeping the player on screen
- acceleration and friction
- queued attacks and combos
- sheets that draw fewer than 8 directions and flip the rest
- `AssetManager`
- integer-only scaling
- unit tests
- Android, iOS and web
- shipping, naming or linking any sprite sheet
