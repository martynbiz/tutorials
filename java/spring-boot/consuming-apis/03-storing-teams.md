# 03: Storing teams

> Written for **Spring Boot 4.1.2** and **Java 25**. See the [series README](README.md) for version notes.

## What you'll learn

- Why the provider's records and your own entities are kept **apart**, with **one place** that maps between them
- How to keep **two ids** for one team: **ours** (the primary key) and **theirs** (`apiId`), and why you need both
- How to **create or update** a team by the provider's id, so importing it twice never makes a second row
- How to work out a **HUD name** from data that's sometimes missing
- Why an HTTP call to the provider must stay **outside** a database transaction, and why that takes **two beans**, not two methods
- How a **Flyway** migration and **`ddl-auto=validate`** keep the schema and the entities honest with each other
- Why tests that share one in-memory database each need **their own data**

By the end, `POST /imports/teams/900001` fetches Riverside Rovers from the provider and stores it in the importer's own database, and `GET /teams` lists what you've stored. Import a team again and you get the same row back, updated, never a copy.

## Concepts

### Their model vs ours

Since guide 01, the importer has had records that mirror API-Football's JSON: `ApiTeam`, `ApiVenue`, `TeamItem`, all in the `provider` package. They describe the provider's world, in the provider's words:

```java
/** A team, exactly as API-Football describes it. {@code code} and {@code country} can be null. */
public record ApiTeam(Long id, String name, String code, String country, Integer founded, boolean national,
        String logo) {
}
```

It's tempting to put `@Entity` on something like that and save it straight away. Don't. The provider's model and yours change for different reasons:

- **The provider changes theirs** when they like: a new API version, a renamed field, a field that becomes `null` for some teams. You'd rather that broke one mapping method than your database.
- **You change yours** when your users need something: a `hudName` the provider doesn't have, a `lastImportedAt` that only makes sense to you, columns sized for what you store.
- **They say things you don't need** (`founded`, `logo`) and **don't say things you do**.

So the series keeps them apart, as the [README](README.md#conventions) promised:

| | The provider's model | Our model |
|---|---|---|
| Where | `com.example.importer.provider` | `com.example.importer.team` |
| Names | `Api*`: `ApiTeam`, `ApiVenue` | Plain: `Team` (and `Player` in guide 04) |
| What it is | A record, shaped exactly like their JSON | A JPA entity, shaped for our database |
| Changes when | API-Football changes | We need something different |

And **only one place maps between them**: a method in this guide's `TeamService` that takes an `ApiTeam` and updates a `Team`. The entity itself never sees `ApiTeam`. If API-Football renames `code` tomorrow, one line changes.

### Two ids for one team

Every team now has two ids:

| Field | Whose | What it's for |
|---|---|---|
| `id` | **Ours**: the primary key, generated by our database | Everything inside our system, including anything that refers to a team, such as guide 04's players |
| `apiId` | **Theirs**: API-Football's id, `900001` for Riverside Rovers | Finding the same team again next time we import. **Unique** |

Why not just use the provider's id as the primary key? Because then someone else's numbering is woven through every foreign key you have. If you ever take data from a second provider, or the provider renumbers something, your own ids shouldn't care. The provider's id is an attribute of the team, like its name: important, unique, but not the thing your tables hang off.

### Create or update, by the provider's id

You'll import the same team many times: every time its squad changes, every time an import is interrupted and started again. Each import has to answer one question first: *do we already have this team?*

The only reliable answer comes from **the provider's id**. Not the name (teams get renamed; two teams can share a name), and certainly not our own `id` (the provider has never heard of it). So:

1. Look up the team **by `apiId`**.
2. Found it? **Update** that row with what the provider says now.
3. Not found? **Create** a new row, with that `apiId`.

This is often called an **upsert** (update or insert). A team is never deleted and created again, which matters: our `id` stays the same for ever, so anything that points at it (guide 04's players) keeps working.

The `unique` constraint on `api_id` is the safety net. If two imports of the same new team ever raced each other, both would find nothing and both would try to insert, and the database would refuse the second rather than store a duplicate. (Guide 05 stops two imports of the same team running at once, so that shouldn't happen. The constraint makes sure it *can't*.)

### The HUD name

The importer's data is for a football game, and the game's heads-up display shows each team in three letters: `RIV 2 - 1 HAR`. API-Football's `code` is exactly that, **when it's there**. For some teams it's `null`.

The rule:

- If the provider's `code` is present (not `null`, not blank), use it **as it is**.
- Otherwise, take the **first three characters of the name**, in capitals. Harbour Athletic, with no code, becomes `HAR`.

Two teams can end up with the same HUD name (Harbour Athletic and Harbour United are both `HAR`). That's accepted: the HUD name is a label, not an id, and the game can live with it.

### HTTP calls stay outside database transactions

Importing a team is two jobs: **fetch** it from the provider (HTTP), then **save** it (database). It's natural to write one `@Transactional` method that does both. Here's why you mustn't.

A transaction holds a **database connection** from the pool for as long as it's open. Spring Boot's pool (HikariCP) has **10** connections by default. An HTTP call to someone else's server can take a few hundred milliseconds on a good day, seconds on a bad one, and (until guide 08 adds timeouts) as long as the provider likes when it's in trouble. Put the HTTP call inside the transaction and:

- **Every import holds a connection while it waits for the provider.** Ten slow imports and the pool is empty: requests that only want to *read* from your database now wait too, because the provider is slow.
- **Any locks the transaction has taken are held for the whole wait.** Other writers queue behind it.
- **A rollback can't undo an HTTP call anyway.** If the save fails, the transaction rolls back your database, but the request has been sent, the provider has counted it against your quota, and nothing can unsend it. The transaction protects nothing on that side.

So the rule for the whole series is: **call the provider first, with no transaction open; then write what it sent in one short transaction.** Guide 04 does many calls per import, and follows the same rule: each write is its own short transaction, and none of them waits on the network.

```
TeamImporter.importTeam(apiId)                      no transaction
 ├── provider.fetchTeam(apiId)        ── HTTP ──▶    (may take seconds)
 └── teamService.saveFromProvider(…)                 @Transactional: begin
       ├── find by api id                               (milliseconds)
       ├── update
       └── save                                      commit
```

### Two beans, not two methods

Why does that picture need **two classes**, `TeamImporter` and `TeamService`? Couldn't `importTeam` call a `@Transactional` method in the same class?

No, and this is the trap. As [todo app 05](../todo-app/05-crud-todo-lists.md) showed, `@Transactional` works through a **proxy**: other beans don't hold your object, they hold a wrapper around it that begins and commits the transaction, then calls the real method. A call from **inside** the object, `this.saveFromProvider(...)`, never goes through the wrapper, so its `@Transactional` is silently ignored.

Putting the save in **another bean** means the call crosses a proxy, and the transaction happens. That's also simply clearer: `TeamService` is "database work for teams", none of which touches the network; `TeamImporter` is "the import", which talks to both.

## Steps

### 1. The table: a Flyway migration

Guide 01 set the database up in `application.properties`, and nothing about it changes now. These are the lines that matter for this guide:

```properties
# H2 database stored in ./data/importer.mv.db
spring.datasource.url=jdbc:h2:file:./data/importer
spring.datasource.username=sa

# Flyway owns the schema; Hibernate only checks it matches the entities
spring.jpa.hibernate.ddl-auto=validate
spring.jpa.open-in-view=false
```

- **The database is a file**, `data/importer.mv.db` inside the `importer` project. It survives restarts, and `data/` is git-ignored (guide 01 added it to `.gitignore`).
- **Flyway owns the schema.** Tables are created and changed only by migrations, which run in order at start-up and are recorded in a `flyway_schema_history` table.
- **`ddl-auto=validate`** tells Hibernate not to create or change anything, only to **check** at start-up that every entity has a table and every field a column of a compatible type. If they disagree, the application refuses to start. Better that than finding out on the first insert.
- **`open-in-view=false`** stops Spring keeping a database session open for the whole web request. That fits this guide: the database is only touched inside the service's short transactions.

Until now, every start logged `No migrations found. Are your locations set up correctly?`. Time to give it one.

In IntelliJ, right-click `src/main/resources` → **New → Directory**, and type `db/migration`. Then right-click the new `migration` folder → **New → File**, and name it `V1__create_team.sql` (a capital `V`, then **two** underscores):

```sql
create table team (
    id               bigint generated by default as identity primary key,
    api_id           bigint                   not null unique,
    name             varchar(100)             not null,
    hud_name         varchar(10)              not null,
    country          varchar(60),
    national         boolean                  not null,
    -- set when a whole import of the team (players included) completes: guide 04
    last_imported_at timestamp with time zone
);
```

- **`id`** is ours. `generated by default as identity` makes the database number new rows 1, 2, 3…
- **`api_id`** is theirs, and **`unique`**: one row per provider team, enforced by the database.
- **`hud_name` is `varchar(10)`**, not 3. It holds the provider's `code` as the provider sends it. The codes you'll see are three letters, but nothing promises that, and guide 07 checks lengths before saving.
- **`country` is the only optional column.** The provider can leave it out; a name and a HUD name we always have.
- **`last_imported_at` stays empty in this guide.** It means "the last time this team was imported *completely*, players and all", and players arrive in guide 04, which sets it. The column is created now so that guide 04 doesn't need a migration of its own just for it.

The table and columns use **snake_case** (`api_id`); the entity in the next step uses Java's **camelCase** (`apiId`). Spring Boot's naming strategy turns one into the other, so you don't need `@Column(name = ...)` on every field.

> **Never edit a migration that has run.** Once `V1` has been applied to a database, Flyway stores its checksum, and refuses to start if the file changes (see Common errors). To change the schema later, you add `V2__…`, then `V3__…`, and so on.

### 2. The `Team` entity

Create `team/Team.java`:

```java
package com.example.importer.team;

import java.time.Instant;
import java.util.Locale;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;

/** A team in OUR database. {@code id} is ours; {@code apiId} is the provider's id for the same team. */
@Entity
public class Team {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, unique = true)
    private long apiId;

    @Column(nullable = false)
    private String name;

    @Column(nullable = false)
    private String hudName;

    private String country;

    private boolean national;

    private Instant lastImportedAt;

    protected Team() {
        // for JPA
    }

    public Team(long apiId) {
        this.apiId = apiId;
    }

    /** Copies what the provider told us. Called for new and existing teams alike. */
    public void update(String name, String code, String country, boolean national) {
        this.name = name;
        this.hudName = hudNameFor(code, name);
        this.country = country;
        this.national = national;
    }

    /** The short name for the game's heads-up display: the provider's code, or else the first three letters. */
    static String hudNameFor(String code, String name) {
        if (code != null && !code.isBlank()) {
            return code;
        }
        return name.substring(0, Math.min(3, name.length())).toUpperCase(Locale.ROOT);
    }

    public Long getId() {
        return id;
    }

    public long getApiId() {
        return apiId;
    }

    public String getName() {
        return name;
    }

    public String getHudName() {
        return hudName;
    }

    public String getCountry() {
        return country;
    }

    public boolean isNational() {
        return national;
    }

    public Instant getLastImportedAt() {
        return lastImportedAt;
    }
}
```

**The two ids have different types, on purpose.** `id` is a `Long`, which is `null` until the database assigns one: that's how Spring Data's `save` tells a new team from an existing one. `apiId` is a `long`, because a team without the provider's id can't exist.

**`new Team(apiId)` is the only public way to make one.** The provider's id is set once, in the constructor, and there's no setter for it: a row never changes which provider team it is. The protected no-argument constructor is for JPA, which needs one to load rows.

**One `update(...)` for new and existing teams alike.** Creating a team is `new Team(apiId)` followed by `update(...)`; updating one is `update(...)` on the row you found. Because both paths run the same method, they can't drift apart: there's no "create" code that sets the HUD name one way and "update" code that forgets to.

**`update` takes plain values, not an `ApiTeam`.** That's "their model vs ours" at work: the entity doesn't import anything from the `provider` package, so a change to the provider's JSON can't reach it.

**The HUD rule** is in `hudNameFor`, a `static` method with no access modifier (package-private), so a test in the same package can call it directly:

- **`code.isBlank()`** treats `""` and `"   "` like `null`: none of them is a usable code.
- **`Math.min(3, name.length())`** means a name shorter than three characters is used whole, rather than throwing `StringIndexOutOfBoundsException`.
- **`toUpperCase(Locale.ROOT)`**, not plain `toUpperCase()`. Without a locale, Java uses the computer's language settings, and some languages capitalise differently: on a machine set to Turkish, `"i".toUpperCase()` is `"İ"`, with a dot. `Locale.ROOT` gives the same answer everywhere.
- **The provider's code is used as it is.** It isn't capitalised or trimmed: what the provider sends is what you store, and guide 07 decides what to do with codes that look wrong.

**Getters, no setters.** Nothing outside the class can set a field directly; everything that changes a team goes through the constructor or `update`.

**`nullable` and `unique` in `@Column`** say what the table promises. With `ddl-auto=validate`, Hibernate doesn't create anything from them; the migration is what enforces the rules. They're there so the entity reads truthfully.

### 4. The repository

Create `team/TeamRepository.java`:

```java
package com.example.importer.team;

import java.util.List;
import java.util.Optional;

import org.springframework.data.jpa.repository.JpaRepository;

public interface TeamRepository extends JpaRepository<Team, Long> {

    Optional<Team> findByApiId(long apiId);

    List<Team> findAllByOrderByNameAsc();
}
```

Two derived queries, which Spring Data writes for you from the method names:

- **`findByApiId`** is the lookup that create-or-update depends on: *do we already have the provider's team 900001?* It returns an `Optional`, because the answer is often "no". The unique index on `api_id` makes it fast.
- **`findAllByOrderByNameAsc`** lists every team by name, for `GET /teams`. (The `All` is only there to make the name read well; `findByOrderByNameAsc` would do the same.)

Notice what's **missing**: there's no `findByName`. Names aren't how you identify a provider's team.

### 5. Create or update: `TeamService`

Create `team/TeamService.java`:

```java
package com.example.importer.team;

import java.util.List;

import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

import com.example.importer.provider.ApiTeam;

/** Database work for teams. Every method is one short transaction, and none of them calls the provider. */
@Service
public class TeamService {

    private final TeamRepository teams;

    public TeamService(TeamRepository teams) {
        this.teams = teams;
    }

    /** Create or update: the provider's id decides whether we already have this team. */
    @Transactional
    public Team saveFromProvider(ApiTeam apiTeam) {
        Team team = teams.findByApiId(apiTeam.id())
                .orElseGet(() -> new Team(apiTeam.id()));
        team.update(apiTeam.name(), apiTeam.code(), apiTeam.country(), apiTeam.national());
        return teams.save(team);
    }

    @Transactional(readOnly = true)
    public List<Team> findAll() {
        return teams.findAllByOrderByNameAsc();
    }
}
```

**`saveFromProvider` is the upsert**, and it's three lines:

1. **`findByApiId(apiTeam.id())`**, and if there's nothing, **`orElseGet(() -> new Team(apiTeam.id()))`**: either the row we already have, or a new, unsaved team with the provider's id. (`orElseGet` takes a lambda, so the new `Team` is only made when it's needed.)
2. **`team.update(...)`** copies the provider's values in, the same way for both.
3. **`teams.save(team)`**. For a new team (`id` is `null`) that's an `INSERT`, and the returned team has its `id`. For one that was found, it's already managed by this transaction, so its changes are written by **dirty checking** when the transaction commits, and `save` just hands it back.

**This is the one place that maps between the two models.** The line with `apiTeam.name(), apiTeam.code(), apiTeam.country(), apiTeam.national()` is the only code in the importer that reads an `ApiTeam` and writes a `Team`. Notice what it *doesn't* copy: `founded` and `logo` stay with the provider.

**`@Transactional`** makes the find, the update and the save one unit, which commits or rolls back together. And it's **short**: everything inside is local database work, milliseconds long. The class comment says it outright: none of these methods calls the provider.

**`@Transactional(readOnly = true)`** on `findAll`, as in the todo app: a read with no dirty checking.

### 6. Fetch, then save: `TeamImporter`

Create `team/TeamImporter.java`:

```java
package com.example.importer.team;

import org.springframework.stereotype.Service;

import com.example.importer.provider.ApiFootballClient;
import com.example.importer.provider.TeamItem;

/**
 * Fetches a team from the provider and stores it.
 * Deliberately NOT @Transactional: the HTTP call can take seconds, and a transaction would hold a database
 * connection (and maybe locks) the whole time. So: call the provider first, then one short transaction.
 */
@Service
public class TeamImporter {

    private final ApiFootballClient provider;
    private final TeamService teamService;

    public TeamImporter(ApiFootballClient provider, TeamService teamService) {
        this.provider = provider;
        this.teamService = teamService;
    }

    public Team importTeam(long apiId) {
        TeamItem item = provider.fetchTeam(apiId);        // HTTP, no transaction
        return teamService.saveFromProvider(item.team()); // its own short transaction
    }
}
```

Two lines of work, and the order is the point:

1. **`provider.fetchTeam(apiId)`**, guide 02's client, with **no transaction open**. Whatever the provider does (answers quickly, slowly, or with an error), no database connection is waiting on it.
2. **`teamService.saveFromProvider(item.team())`**, a call to **another bean**, so it goes through `TeamService`'s proxy and gets its `@Transactional`. The transaction begins here and commits before the method returns.

**If the provider fails, nothing is written.** `fetchTeam` throws one of guide 02's exceptions (`NotFoundAtProviderException`, `ProviderRejectedException`, `ProviderHttpException`) before `saveFromProvider` is ever called. A team you already had stays exactly as it was. A test in step 9 proves it.

The comment at the top is for the next developer, who'll look at this class, think "an import should be one transaction" and add `@Transactional`. It tells them why not.

### 7. The endpoints: `TeamController`

Create `team/TeamController.java`:

```java
package com.example.importer.team;

import java.time.Instant;
import java.util.List;

import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class TeamController {

    private final TeamImporter importer;
    private final TeamService teamService;

    public TeamController(TeamImporter importer, TeamService teamService) {
        this.importer = importer;
        this.teamService = teamService;
    }

    /** Imports one team now and waits for it. (Guide 05 moves imports into the background.) */
    @PostMapping("/imports/teams/{apiId}")
    public TeamView importTeam(@PathVariable long apiId) {
        return TeamView.from(importer.importTeam(apiId));
    }

    @GetMapping("/teams")
    public List<TeamView> teams() {
        return teamService.findAll().stream().map(TeamView::from).toList();
    }

    public record TeamView(Long id, long apiId, String name, String hudName, String country, boolean national,
            Instant lastImportedAt) {

        static TeamView from(Team team) {
            return new TeamView(team.getId(), team.getApiId(), team.getName(), team.getHudName(),
                    team.getCountry(), team.isNational(), team.getLastImportedAt());
        }
    }
}
```

**`POST /imports/teams/{apiId}`** imports the team with the **provider's** id. It's a `POST` because it changes our data, and the URL names what you're asking for: an import of a team. For now it does the whole import while you wait and answers **`200 OK`** with the stored team.

That's fine for one request to the provider. In guide 04 an import becomes dozens of requests, and can take minutes, which is far too long for an HTTP request to wait. **Guide 05 changes this same URL** to answer straight away with **`202 Accepted`** and a `Location` header pointing at the import's status, while the work carries on in the background. The URL stays; the conversation changes.

**`GET /teams`** lists the stored teams, by name. It reads **only our database**: it works with the fake provider stopped. That's the "serve from ours" half of the [README](README.md)'s promise.

**`TeamView`** is the JSON shape of a team, a record nested in the controller. The controller never returns the entity itself: what goes over the wire is decided here, not by whatever fields `Team` happens to have. It's "their model vs ours" again, pointing outwards this time.

**Errors need nothing new.** An unknown team, or a provider in trouble, throws the same exceptions as guide 02's `GET /provider/teams/{id}`, and guide 02's `ApiExceptionHandler` turns them into a `404` or a `502` `ProblemDetail`, whichever controller they came from.

> **No security yet.** Anyone who can reach port 8080 can start an import. Guide 05 puts the import endpoints behind HTTP Basic.

> **Done the REST API series?** A response record with a static `from(entity)` is the same pattern as its `EventResponse`. Skim this step.

### 10. Tests: one shared in-memory database

Before writing the import tests, one thing to know about the test database. Every test class marked `@ImporterIntegrationTest` (guide 01) uses the same URL:

```java
@SpringBootTest(properties = "spring.datasource.url=jdbc:h2:mem:importer-test;DB_CLOSE_DELAY=-1")
```

- **`mem:importer-test`** is an in-memory database, named `importer-test`. Anything in the same JVM that opens that name gets **the same database**.
- **`DB_CLOSE_DELAY=-1`** keeps it alive until the JVM exits, instead of throwing it away when the last connection closes.

Each WireMock test class gets its own Spring context (its `@DynamicPropertySource` sets a different `api-football.base-url`, so Spring can't reuse another class's context). But `./mvnw test` runs them all in one JVM, so they all share **one** `importer-test` database. Teams stored by one class are still there when the next one runs.

That's harmless as long as tests don't trip over each other's data. Two habits make sure of it:

- **Each test class uses its own provider ids.** `TeamImporterTest` uses 900021 to 900023 and 900120; `TeamApiTest` uses 900031 to 900039. One class can never "update" a team another class created.
- **Never assert an exact list.** `GET /teams` returns whatever every class has stored so far, in whatever order the classes ran. Assert that it **contains** your team, not that it **is** your team.

The fixture ids in the fake provider (900001, 900002, 900100) aren't used by the tests at all: tests build their own replies with guide 01's `ProviderJson` helper.

### 11. Test the importer

Create `src/test/java/com/example/importer/team/TeamImporterTest.java`:

```java
package com.example.importer.team;

import static com.github.tomakehurst.wiremock.client.WireMock.equalTo;
import static com.github.tomakehurst.wiremock.client.WireMock.get;
import static com.github.tomakehurst.wiremock.client.WireMock.okJson;
import static com.github.tomakehurst.wiremock.client.WireMock.serverError;
import static com.github.tomakehurst.wiremock.client.WireMock.urlPathEqualTo;
import static com.github.tomakehurst.wiremock.core.WireMockConfiguration.wireMockConfig;
import static org.assertj.core.api.Assertions.assertThat;
import static org.assertj.core.api.Assertions.assertThatExceptionOfType;

import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.extension.RegisterExtension;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.test.context.DynamicPropertyRegistry;
import org.springframework.test.context.DynamicPropertySource;

import com.example.importer.ImporterIntegrationTest;
import com.example.importer.provider.ProviderHttpException;
import com.example.importer.provider.ProviderJson;
import com.github.tomakehurst.wiremock.junit5.WireMockExtension;

@ImporterIntegrationTest
class TeamImporterTest {

    @RegisterExtension
    static WireMockExtension provider = WireMockExtension.newInstance()
            .options(wireMockConfig().dynamicPort())
            .build();

    @DynamicPropertySource
    static void providerUrl(DynamicPropertyRegistry registry) {
        registry.add("api-football.base-url", provider::baseUrl);
    }

    @Autowired
    TeamImporter importer;

    @Autowired
    TeamRepository teams;

    @Test
    void createsANewTeam() {
        stubTeam(900021, ProviderJson.team(900021, "Riverside Rovers", "RIV", "England", false));

        importer.importTeam(900021);

        Team team = teams.findByApiId(900021).orElseThrow();
        assertThat(team.getId()).isNotNull();
        assertThat(team.getName()).isEqualTo("Riverside Rovers");
        assertThat(team.getHudName()).isEqualTo("RIV");
        assertThat(team.getCountry()).isEqualTo("England");
        assertThat(team.isNational()).isFalse();
        assertThat(team.getLastImportedAt()).isNull();
    }

    @Test
    void updatesTheSameRowWhenImportedAgain() {
        stubTeam(900022, ProviderJson.team(900022, "Harbour Athletic", null, "Scotland", false));
        Team first = importer.importTeam(900022);
        assertThat(first.getHudName()).isEqualTo("HAR");

        stubTeam(900022, ProviderJson.team(900022, "Harbour Athletic FC", "HAF", "Scotland", false));
        Team second = importer.importTeam(900022);

        assertThat(second.getId()).isEqualTo(first.getId());
        Team stored = teams.findByApiId(900022).orElseThrow();
        assertThat(stored.getName()).isEqualTo("Harbour Athletic FC");
        assertThat(stored.getHudName()).isEqualTo("HAF");
    }

    @Test
    void marksNationalTeams() {
        stubTeam(900120, ProviderJson.team(900120, "Scotland", "SCO", "Scotland", true));

        importer.importTeam(900120);

        assertThat(teams.findByApiId(900120).orElseThrow().isNational()).isTrue();
    }

    @Test
    void storesNothingWhenTheProviderFails() {
        provider.stubFor(get(urlPathEqualTo("/teams")).withQueryParam("id", equalTo("900023"))
                .willReturn(serverError()));

        assertThatExceptionOfType(ProviderHttpException.class).isThrownBy(() -> importer.importTeam(900023));
        assertThat(teams.findByApiId(900023)).isEmpty();
    }

    private void stubTeam(long id, String json) {
        provider.stubFor(get(urlPathEqualTo("/teams")).withQueryParam("id", equalTo(String.valueOf(id)))
                .willReturn(okJson(json)));
    }
}
```

The WireMock set-up at the top is guide 02's, unchanged. What's new:

- **The tests check the database, not just the return value.** They autowire `TeamRepository` and look the team up with `findByApiId`, the same lookup the upsert uses. A test that only checked what `importTeam` returned would pass even if nothing were saved.
- **`updatesTheSameRowWhenImportedAgain`** is the upsert's test. The provider's answer changes between the two imports (it gains the code `HAF`, and a new name), just as a real provider's data changes between your imports. The second import must keep **our `id`** and pick up both changes, including the HUD name, which now comes from the code instead of the name.
- **`stubTeam` is called twice for the same id.** WireMock uses the **most recently added** stub when two match the same request equally, so the second import sees the new reply.
- **`storesNothingWhenTheProviderFails`** proves the order in `TeamImporter`: a `500` throws `ProviderHttpException` (guide 02), and there's no row for 900023 afterwards.
- **`stubTeam`** is a small private helper: stub `GET /teams?id={id}` with a given reply. `ProviderJson.team(...)` (from guide 01) builds the reply in the provider's exact shape; pass `null` as the code for a team without one.
- **Ids 900021 to 900023 and 900120**, this class's own, as step 10 explained.

    @Autowired
    MockMvcTester mvc;

### Exercise 4: one bean instead of two

A colleague thinks two classes is one too many. They move `saveFromProvider`, with its `@Transactional`, into `TeamImporter`, and change `importTeam` to call `this.saveFromProvider(item.team())`. They delete `TeamService`. Answer without running anything:

1. Does `saveFromProvider` still run in a transaction? Would the tests notice?
2. A reviewer spots the problem, and suggests putting `@Transactional` on `importTeam` instead. Now it's definitely transactional. What's wrong with that?

<details>
<summary>Solution</summary>

1. **No.** `importTeam` calls `this.saveFromProvider(...)`, a call from inside the object, which never passes through Spring's proxy. Its `@Transactional` is silently ignored. The tests would very likely still pass, because `save` from Spring Data has a transaction of its own, so the row still gets written. That's what makes the bug dangerous: the lookup and the save are no longer one unit, and nothing tells you. (This is the self-invocation rule from [todo app 05](../todo-app/05-crud-todo-lists.md).)
2. Now **the HTTP call is inside the transaction**. Every import holds a database connection while it waits for the provider: ten slow imports and the pool is empty, and requests that only read the database wait behind them. The rollback it buys protects nothing on the provider's side, either: the request has been sent and counted. The fix is the design from steps 5 and 6: a separate `TeamService` bean for the database work, called **after** the HTTP call.

</details>

## Common errors

**`Schema validation: missing column [hud_name] in table [team]`**
The importer won't start. In full, the log says `Error creating bean with name 'entityManagerFactory'` and ends:

```
Caused by: org.hibernate.tool.schema.spi.SchemaManagementException: Schema validation: missing column [hud_name] in table [team]
```

That's `ddl-auto=validate` doing its job: the entity has a `hudName` field, so Hibernate expects a `hud_name` column, and the table doesn't have one. Here, the migration said `hud` instead. Check the column names in `V1__create_team.sql` against the fields in `Team`, remembering that `camelCase` becomes `snake_case`. If V1 has already run on your `data/` database, fixing the file leads straight to the next error.

**`Migration checksum mismatch for migration version 1`**
You changed `V1__create_team.sql` after it had run against `data/importer`:

```
Validate failed: Migrations have failed validation
Migration checksum mismatch for migration version 1
-> Applied to database : 2111597158
-> Resolved locally    : -362690128
Either revert the changes to the migration, or run repair to update the schema history.
```

(Your numbers will differ.) Flyway recorded V1's checksum when it ran, and the file no longer matches, so it refuses to guess which is right. The real fix is to put V1 back as it was and make your change in a new `V2__….sql`. While you're developing on your own machine, and the data doesn't matter, you can instead stop the importer, delete the `data` folder, and start again: Flyway runs the edited V1 on an empty database. Never do that to a database anyone else depends on.

**`Database may be already in use: "…/importer/data/importer.mv.db"`**
A second copy of the importer is running (often one in IntelliJ and one in a terminal), and H2's file database allows one process at a time. Stop the extra copy. Stop the importer before you delete `data/`, too: the file is in use while it runs.

**`POST /imports/teams/…` gives `500`, and the log says `ResourceAccessException: I/O error on GET request for "http://localhost:8089/teams": null`**
The fake provider isn't running. Start it first, then import. (Guide 08 turns this into a proper answer: by then imports run in the background, so the import ends `FAILED` with `API-Football could not be reached (ConnectException)`, and `GET /provider/teams/{id}` answers `502`.) `GET /teams` still works without it, because it only reads our database.

> **Sidebar: PostgreSQL or MySQL instead of H2.** The series uses an H2 file database because there's nothing to install. A real importer would use a database server. This is **the configuration you'd change**, not something the series runs, and **none of it was tested for this series** (no database servers or Docker were used). Check the versions and details against the documentation.
>
> **Dependencies.** Each database needs its JDBC driver **and** a Flyway module. Since Flyway 10, support for most databases lives in separate modules; H2's is built in, which is why you haven't needed one. Leave out the Flyway module and the importer fails at start-up with Flyway's `Unsupported Database` error. Spring Boot manages all four versions, so no `<version>` is needed. For PostgreSQL:
>
> ```xml
> <dependency>
>     <groupId>org.postgresql</groupId>
>     <artifactId>postgresql</artifactId>
>     <scope>runtime</scope>
> </dependency>
> <dependency>
>     <groupId>org.flywaydb</groupId>
>     <artifactId>flyway-database-postgresql</artifactId>
> </dependency>
> ```
>
> For MySQL, `com.mysql:mysql-connector-j` (runtime) and `org.flywaydb:flyway-mysql`. The tests could keep using in-memory H2, but then they'd no longer run against the kind of database you deploy to, which is a trade-off worth making on purpose rather than by accident.
>
> **Properties.** Only the connection changes:
>
> ```properties
> spring.datasource.url=jdbc:postgresql://localhost:5432/importer
> spring.datasource.username=${DB_USERNAME}
> spring.datasource.password=${DB_PASSWORD}
> ```
>
> (or `jdbc:mysql://localhost:3306/importer`). The username and password come from environment variables, like the API-Football key, and are never committed. Flyway, `ddl-auto=validate` and `open-in-view=false` stay exactly as they are.
>
> **The migration.** PostgreSQL accepts `V1__create_team.sql` as written: `generated by default as identity`, `boolean` and `timestamp with time zone` are all PostgreSQL. MySQL doesn't. It needs `auto_increment` for the id and has no `timestamp with time zone`, so `last_imported_at` becomes a plain date-time that you keep in UTC:
>
> ```sql
> create table team (
>     id               bigint auto_increment primary key,
>     api_id           bigint       not null unique,
>     name             varchar(100) not null,
>     hud_name         varchar(10)  not null,
>     country          varchar(60),
>     national         boolean      not null,
>     last_imported_at datetime(6)
> );
> ```
>
> (`timestamp(6)` works too. MySQL accepts `boolean` and stores it as `tinyint(1)`.) If you ever need to support more than one database, Spring Boot can keep a migrations folder per database with `spring.flyway.locations=classpath:db/migration/{vendor}`.
>
> **What doesn't change** is everything this guide is about: two ids, a unique `api_id`, create-or-update by the provider's id, and HTTP outside transactions. Those carry over to any database unchanged.

## Recap

- The provider's records (`Api*`, in `provider`) and our entities (`Team`, in `team`) are **separate models**. **One method**, `TeamService.saveFromProvider`, maps between them, and the entity never sees the provider's types.
- A team has **two ids**: **our** primary key, and the provider's **`apiId`**, unique. Our tables hang off our id.
- **Create or update by `apiId`**: find it or make a new one, then run the **same `update`** either way. A team is never re-created, so our `id` never changes. The **unique constraint** backs that up.
- The **HUD name** is the provider's code if there is one, else the first three letters of the name in capitals, with **`Locale.ROOT`**. Clashes are allowed.
- **HTTP calls stay outside transactions**: fetch first, with nothing open, then save in one **short** transaction. A transaction waiting on the network holds a pooled connection, and its rollback can't undo the request anyway.
- That takes **two beans**, `TeamImporter` and `TeamService`, because `@Transactional` works through the **proxy**, and a call to `this` bypasses it.
- **Flyway** owns the schema (`V1__create_team.sql`); **`ddl-auto=validate`** refuses to start when the entities and tables disagree. Never edit a migration that has run.
- `last_imported_at` exists from V1 but stays **`null`** until guide 04 imports a team completely.
- `POST /imports/teams/{apiId}` waits and returns **`200`** with the team, for now; guide 05 makes the same URL answer **`202 Accepted`**. `GET /teams` serves from **our** database only.
- Test classes share **one in-memory database**: each uses **its own ids**, and lists are checked with **`contains`**.

### Interview angle

<details>
<summary>"Why store the provider's id in its own column, rather than using it as your primary key?"</summary>

Because your schema shouldn't depend on someone else's numbering. Your own generated key is what your foreign keys and your own API use; the provider's id is an attribute you need for one job, finding the same record again when you sync. Keeping them apart means you can take data from a second provider, survive a provider renumbering or merging records, or store something the provider doesn't know about, without touching your relationships. The provider's id still gets a unique constraint, because "one row per provider record" is a real rule.

</details>

<details>
<summary>"Why shouldn't you call an external API inside a database transaction?"</summary>

A transaction holds a connection from a small pool (HikariCP's default is 10), and any locks it has taken, for as long as it's open. An HTTP call can take seconds, or much longer without timeouts, so slow responses from the provider start starving the rest of the application of database connections. And the transaction buys nothing on the remote side: a rollback can't unsend the request, which has already been made and probably counted against a quota. So you make the call first, with no transaction, then write the result in a short transaction of its own.

</details>

<details>
<summary>"A `@Transactional` method isn't starting a transaction. What's a likely cause?"</summary>

Self-invocation. Spring implements `@Transactional` with a proxy around the bean, so only calls that come in through the proxy, from another bean, get a transaction. A call from another method in the same class (`this.save(...)`) goes straight to the object and the annotation is ignored. It's often hidden because repository methods have transactions of their own, so the code still appears to work. The usual fix is to move the transactional method into a separate bean. (Other causes: the method isn't public, or the object wasn't created by Spring at all.)

</details>

<details>
<summary>"How do you import the same record repeatedly without creating duplicates?"</summary>

Create-or-update keyed on the provider's id: look the record up by that id, create it only if it's not there, and apply the same update either way, inside one transaction. Back it with a unique constraint on the provider's id, so even two imports racing each other can't both insert: the database rejects the second. Never key it on something like a name, which changes and isn't unique, and never delete and re-insert, which would change your own id and break everything that refers to it.

</details>

<details>
<summary>"Why use Flyway with `ddl-auto=validate` instead of letting Hibernate update the schema?"</summary>

`ddl-auto=update` lets Hibernate change your database to match the entities at start-up. It can add, but it won't safely rename, drop or move data, and what it did isn't written down anywhere you can review. Migrations are explicit SQL, versioned in source control, run in the same order on every database, and recorded in a history table. `validate` then gives you a check at start-up that the entities and the migrated schema agree, so a mismatch fails immediately rather than on the first query that touches it.

</details>
